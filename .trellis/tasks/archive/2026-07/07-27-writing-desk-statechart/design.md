# WritingDesk Statechart Design

## 1. Ownership Boundaries

```text
PostgreSQL ChapterWorkflowRun + JobEvent
  |  current lookup / command snapshot / cursor replay
  v
Vue Query
  |  owns Project, Chapter, Workflow connection/snapshot cache
  v
XState actor
  |  owns workflow interaction + transport health + command correlation
  v
WritingDesk components
     own drawer/modal/focus/version-detail/selection presentation only
```

Invariants:

- backend snapshot is lifecycle truth;
- Vue Query is the only refetchable server cache;
- XState context stores no `NovelProject`, `Chapter`, candidate list, evaluation body or project chapter list;
- Vue refs do not mirror workflow status;
- one selected `(projectId, chapterNumber)` scope has one live actor and one event connection epoch.

## 2. Backend Current Lookup Contract

### 2.1 Public shape

Add a reusable transport model:

```text
ChapterWorkflowConnection
  snapshot: ChapterWorkflowSnapshot
  events_url: string
```

`ChapterWorkflowStartResponse` reuses this shape and adds `created`. The new endpoint is:

```text
GET /api/writer/chapter-workflows/current
  ?project_id=<uuid>
  &chapter_number=<positive-int>

200 ChapterWorkflowConnection | null
```

The static route is registered before `/chapter-workflows/{run_id}`. `events_url` is generated by one router helper and treated as opaque transport metadata by the frontend; the frontend does not reconstruct the tasks path.

### 2.2 Repository selection

The owner-scoped repository query filters `user_id + project_id + chapter_number` and accepts only:

```text
is_active = true
OR
(
  is_active = false
  AND status IN (successful, failed, cancelled)
  AND successor_run_id IS NULL
)
```

Ordering is deterministic:

```text
is_active DESC,
base_revision DESC,
updated_at DESC,
created_at DESC,
id DESC
```

This makes any active lineage win, chooses the newest chapter revision when an invariant breach leaves multiple active revisions, and prevents a superseded predecessor from becoming the refresh target. No accessible candidate returns `null`; foreign and missing scopes are therefore indistinguishable and cannot expose another user's run id.

The service builds the existing `ChapterWorkflowSnapshot`, including a cursor read from the same durable workflow stream. If a concurrently changed snapshot reports `successor_run_id`, the service follows the owner-scoped successor once and otherwise asks the client to refetch; it never returns a predecessor as a writable command target.

### 2.3 Contract release unit

The route/schema change updates together:

```text
Pydantic schema
  -> deterministic backend/openapi.json
  -> frontend generated schema.d.ts
  -> generated aliases + runtime decoder
  -> query/mutation consumers
```

No ORM column or Alembic migration is required.

### 2.4 Exhaustive public enums

Before generating frontend types, tighten the snapshot contract so the state matrix has a finite source of truth:

```text
ChapterWorkflowRunStatus
  queued | running | retry_wait | waiting_for_selection | finalizing
  | projection_pending | needs_attention | successful | failed
  | cancelled | superseded

ChapterWorkflowRootJobStatus
  queued | running | retry_wait | waiting | succeeded | failed
  | dead_letter | needs_attention | cancelled

ChapterWorkflowNodeKeyV1
  existing V1 node-key Literal
```

`workflow_version`, `state_schema_version` and `context_schema_version` are `Literal[1]` for the V1 response. `ChapterWorkflowSnapshot` uses these aliases instead of unrestricted strings/integers, so OpenAPI emits unions and Pydantic fails closed if persistence contains an unknown value.

The runtime decoder keeps readonly value arrays for actual JSON checks and uses a type-level equality assertion against the generated unions. A backend enum addition therefore requires the decoder list and transition table to change in the same release unit; missing or extra values fail type-check/tests.

## 3. Frontend Transport And Cache

### 3.1 API boundary

Create one workflow API domain using `requestJson`/`authJson` and generated indexed aliases for:

- connection/current response;
- start request/response;
- workflow snapshot;
- command envelope/response;
- typed 409 conflict response.

One runtime decoder accepts `unknown` and validates the connection, snapshot schema versions, run/scope identity, revisions, cursor, statuses and command list. `HttpRequestError.payload` is decoded for 409; malformed or unsupported payloads become a typed contract error.

When `retry_external` is allowed, the snapshot exposes the deterministic public
`retry_activity_key` chosen from the owner-scoped canonical ambiguous activities. The
UI submits that opaque key only after explicit duplicate-risk acknowledgement; it
must not derive an activity identity from `node_key`, error text or task payloads.

The existing task SSE parser/decoder is reused. Its connection URL comes from `events_url`; its expected scope is always `{ stream_type: 'workflow', stream_id: runId }`.

### 3.2 Vue Query ownership

Add one domain key factory and a canonical current query:

```text
chapterWorkflowQueryKeys.current(projectId, chapterNumber)
```

Start and command mutations write their decoded snapshot into that current cache. A typed 409 does the same before surfacing a recoverable conflict result. The WritingDesk actor reads reconciliation events derived from this cache; it does not own another copy.

Project/chapter invalidation is revision-aware:

- invalidate Chapter + Project when `current_chapter_revision` increases;
- invalidate at first transition into `waiting_for_selection`, `projection_pending` or a terminal state when the UI projection may have changed;
- do not invalidate for every progress event or transport reconnect.

The Chapter read keeps the legacy `versions: string[]` field for rollback clients and
adds a sanitized `version_selections` projection containing only version id, content,
label and source workflow run id. WritingDesk filters that Vue Query-owned list by the
current run before issuing `select`; it never derives a durable version id from an
array index and never copies the candidate list into XState context.

## 4. Statechart Model

Use exact dependencies:

```text
xstate         5.32.5
@xstate/vue    5.0.1
```

`@xstate/vue` 5.0.1 requires `xstate ^5.32.5`; both application dependencies are stored without caret. The pure machine and its Vue integration stay in the existing `composables/` boundary; server query hooks remain in `queries/`.

### 4.1 Top-level states

```text
booting
  |
  +-- lookup success -----------------------------------+
  |                                                     v
  +-- contract/auth failure --> fatal        ready (parallel)
                                                |
                         +----------------------+----------------------+
                         |                                             |
                    workflow                                      transport
                         |                                             |
       idle / submitting / running                   disconnected / connecting
       waitingForSelection / finalizing              connected / reconnecting
       projectionPending / succeeded                 polling
       failed / cancelled / superseded
```

Transport transitions never replace workflow phase. `fatal` is reserved for bootstrap/auth/contract failures that prevent a trustworthy state; a workflow `failed` snapshot remains a normal, recoverable business phase.

### 4.2 Context

Context is bounded to:

```text
projectId, chapterNumber, scopeEpoch,
runId, rowRevision, chapterRevision,
checkpointId, resumeCursor, allowedCommands, retryActivityKey,
pendingCommandId, lastContractError, lastCommandError
```

Errors are normalized public strings/categories with bounded length. Full HTTP payloads, Chapter data and event history do not enter context.

### 4.3 Snapshot mapping

```text
queued / running / retry_wait    -> running
waiting_for_selection            -> waitingForSelection
finalizing                       -> finalizing
projection_pending               -> projectionPending
successful                       -> succeeded
failed / needs_attention         -> failed
cancelled                        -> cancelled
superseded                       -> superseded
null connection                  -> idle
```

`retry_wait` remains a running durable process; `needs_attention` is failed from the user's perspective but only the server-provided `allowed_commands` decides whether retry, acknowledged external retry or cancel is legal.

### 4.4 Commands and guards

- `START` is legal only in idle or cancelled with no pending command. Cancelled starts a new durable run; succeeded remains terminal and has no regenerate shortcut.
- `SELECT_VERSION`, `RETRY`, `RETRY_EXTERNAL`, `RETRY_PROJECTION` and `CANCEL` require the matching server command in `allowed_commands`, a current checkpoint and no pending command.
- Every dispatch creates one UUID `command_id` and freezes expected run/chapter revision plus checkpoint.
- A repeated click while `pendingCommandId` is set is ignored.
- 202 response or typed 409 snapshot reconciles cache and machine; neither path guesses a terminal phase.
- A response for an old scope epoch, run id or lower `row_revision` is ignored.
- Request correlation and snapshot applicability are separate: a correlated response for a
  superseded run clears the pending command but cannot replace the newer run snapshot.

There is no separate `FINALIZE` wire command: selecting a version sends the durable `select` command, whose workflow transition owns finalization. There is no separate manual evaluate command: review is a workflow node and review recovery uses allowed retry commands.

### 4.5 User-visible selectors

- waiting without query-visible candidates renders “候选版本同步中” and disables selection; it first invalidates/refetches Chapter data instead of submitting an empty command;
- `projectionPending` distinguishes “正文已提交” from “整章生成失败” and exposes retry/cancel only when returned by `allowed_commands`;
- `needs_attention` displays the public error plus an explicit “可能重复外部调用” acknowledgement before `retry_external`;
- failed displays the public error and only generated allowed actions;
- cancelled offers a new start; succeeded offers no workflow action;
- superseded disables all commands and immediately reruns current lookup;
- contract failure disables workflow commands and offers resync; 401 follows the existing auth logout/login path.

## 5. Actors And Recovery

### 5.1 Actor ports

The pure machine receives injected ports rather than importing API modules:

- current query refetch;
- start mutation;
- command mutation;
- task stream subscription;
- revision-aware Chapter/Project invalidation;
- reconnect clock/backoff.

The Vue-facing composable wires ports already created by `queries/`; it does not call `fetch` or create a second QueryClient. `useMachine` owns actor mount/unmount; invoked stream actors abort and unsubscribe when scope/state exits.

### 5.2 Bootstrap and scope change

1. Selected project/chapter changes and increments `scopeEpoch`.
2. Old invoked stream is stopped before its cache/actor callbacks can apply.
3. Current query returns `ChapterWorkflowConnection | null` and decoder verifies scope.
4. Machine reconciles the snapshot or enters idle.
5. For a run, transport connects to returned `events_url` from `resume_cursor`.

Late callbacks carry the captured epoch and run id. Guards reject them after a scope change even if AbortController cancellation races with an already queued callback.

### 5.3 Event wake-up

An accepted durable task event does not map task status to workflow status. It only requests a current snapshot refetch. A newer decoded `row_revision` is then sent as `SNAPSHOT_RECONCILED`.

Duplicate cursor events are ignored. A cursor gap/reset stops the old connection, fetches a fresh connection/snapshot/cursor pair, atomically replaces cache context, then reconnects. Exponential reconnect is bounded; after the threshold, a long Vue Query polling fallback remains active while the workflow region stays unchanged.

Concurrent current refetches also carry a monotonic request epoch. Only the last initiated
refetch may apply `null` or connection metadata; `row_revision` remains the business-snapshot
ordering guard. This prevents a slower earlier `null` response from clearing a newer run.

### 5.4 Rehydration

Browser reload does not restore a locally persisted XState snapshot. It reconstructs the actor from server connection/snapshot + durable cursor, avoiding stale browser state as a second fact source. XState persisted-snapshot support is used only for focused runtime tests if useful, not for product recovery.

## 6. Direct Cutover

### 6.1 Removed lifecycle ownership

Cutover removes or disconnects from WritingDesk:

- `generatingChapter`, `evaluatingChapter`, `chapterGenerationResult` lifecycle mirrors;
- local `generation_status` optimistic writes and failure rollback;
- `WDWorkspace` status/content watcher that starts chapter SSE;
- `useWritingDeskProject` stream key, reconnect timer and lifecycle cache upsert;
- duplicate `waitForCompletion` + refresh/refetch chains in old generation/evaluation/finalize mutations;
- calls to legacy generate/evaluate/finalize endpoints from WritingDesk.

Pure presentation/navigation behavior remains: selected chapter, selected version index, drawer/modal/focus state, detail loading, sidebar scroll and text/ARIA rendering. Delete/edit/optimization commands remain outside this workflow unless their existing caller becomes orphaned by the cutover.

### 6.2 Release gate

Backend Settings keeps `default=False`. The Docker application environment requires an explicit `CHAPTER_WORKFLOW_START_ENABLED` value; tracked env examples, server provisioning script and deployment docs set it to `true` for this release. Missing release configuration fails Compose expansion rather than silently serving a new frontend against a disabled API.

Deployment order:

```text
1. deploy compatible backend with gate still false
2. verify current/start/command API and worker readiness
3. set gate true and restart app release unit
4. deploy the statechart frontend
5. run browser smoke and monitor workflow/task metrics
```

Old HTTP facades and compatibility adapters remain. With the gate enabled, old generation requests route to the same durable workflow owner; an existing active run remains durable-owned even if rollback later disables new starts.

Before deploying the statechart frontend, an automated compatibility drill runs with the gate enabled: submit through the legacy generate facade, resolve the same run through current lookup, then submit/repeat the supported command path and assert one run, one accepted command identity and one canonical outcome. This makes the temporary old-frontend/gate-enabled window an explicit release contract rather than an assumption.

### 6.3 Rollback

Rollback order is the reverse ownership handoff:

```text
1. deploy the previous frontend
2. verify old facade can observe/drain active durable runs
3. set CHAPTER_WORKFLOW_START_ENABLED=false for new starts
4. keep backend schema/events/checkpoints; do not roll back canonical revisions
```

The new frontend cannot be kept while only toggling the backend gate off. Binary/frontend rollback and gate rollback are one operational action.

The rollback drill deploys or emulates the previous frontend facade, leaves an active durable run in flight, switches new starts off, and proves the compatibility adapter continues to observe/drain that run without enqueueing a second legacy job. It records the run id, root job id, command id(s), final canonical revision and duplicate-count assertions as the acceptance artifact; no private payload or secret is recorded.

## 7. Testing Strategy

### Backend

- repository ordering across active revisions and terminal lineages;
- exclusion of superseded/successor predecessors;
- owner isolation and null behavior;
- static route precedence and connection response;
- snapshot/cursor consistency and concurrent successor handling;
- exhaustive workflow/root-job/node enums and unknown-value failure;
- old-facade/gate-enabled cutover plus active-run/gate-disabled rollback ownership drill;
- deterministic OpenAPI and generated ownership checks.

### Frontend unit/integration

- decoder good/base/bad/version/scope cases;
- table-driven status and event transitions;
- every command guard, duplicate dispatch and stale response;
- parallel transport transitions preserve workflow phase;
- current null, refresh rehydrate, 202/409 cache reconciliation;
- stream replay/reset/scope change/late callback/poll fallback;
- revision-aware Chapter/Project invalidation;
- retained task reminder semantics.

### Browser

Pin `@playwright/test@1.62.0`, add `playwright.config.ts` plus the `test:e2e` npm script, and use Chromium with deterministic API/SSE fixtures. Keep the suite focused on one WritingDesk route and the critical branches: waiting refresh, waiting-without-candidates, disconnect/replay, double click, stale event rejection, projection retry, cancelled restart, superseded follow, fatal contract error and ARIA-visible status. Any service started for this check is stopped before task completion.

### Bundle

Capture a clean pre-XState production build and compare it with the final build using the existing manifest/gzip budget script. Record total JS gzip, WritingDesk-related chunk gzip and the delta. Existing hard budgets are not raised as part of this task; package unpacked size is not evidence of browser cost.

## 8. Key Risks

| Risk | Control |
| --- | --- |
| current lookup chooses stale lineage | active-first deterministic order, successor exclusion/follow, stale run/revision guards |
| SSE notification is mistaken for workflow fact | every event refetches decoded workflow snapshot |
| transport reconnect erases business phase | parallel workflow/transport regions |
| 202/409 races with SSE | single current query cache + monotonic row revision |
| old/new UI both submit | direct frontend cutover; compatibility facade routes active runs to durable owner |
| gate disabled under new frontend | required release env + ordered deployment + browser smoke |
| XState adds excessive bundle cost | route chunk measurement and existing hard budget, no threshold increase |
| browser tests become broad/flaky | deterministic fixtures and one focused Chromium project |
