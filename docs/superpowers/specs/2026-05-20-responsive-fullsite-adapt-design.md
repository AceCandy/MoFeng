# MoFeng 全站响应式适配设计（桌面优先补移动）

## 1. 背景与目标

### 1.1 背景
MoFeng 当前是以桌面优先的工作流产品，包含作者侧（工作台、灵感、项目详情、写作台、设置）与管理侧（管理首页、管理项目详情）两类界面。现有交互和布局在桌面可用，但在平板和手机场景下存在信息拥挤、操作路径过长、触控可达性不足等风险。

### 1.2 目标
本次适配目标为：
- 覆盖全站路由，不仅是作者主流程。
- 采用“桌面优先补移动”策略，在保持桌面稳定性的前提下补齐平板与手机完整可用性。
- 允许移动端导航结构重排，以保障移动端关键任务可操作。

### 1.3 结果定义
适配完成后，用户在手机和平板上可完成与桌面同等级别的关键任务，不出现“只能看不能改”的核心功能断层。

## 2. 约束与前提

### 2.1 已确认约束
- 适配范围：全站覆盖。
- 断点基线：桌面优先补移动。
- 移动目标：完整可用。
- 导航策略：允许重排。

### 2.2 产品语义约束
保持 MoFeng 既有产品语义：安静、专业、低噪声，不引入营销化风格或夸张视觉结构。适配重点在可操作性与结构清晰，不是视觉重设计。

## 3. 响应式分层与断点策略

### 3.1 断点定义
- Desktop：`>=1200px`
- Tablet：`834px-1199px`
- Mobile：`<834px`

### 3.2 实现策略
- 使用桌面样式作为基础层。
- 使用两层覆盖媒体查询：`@media (max-width: 1199px)`、`@media (max-width: 833px)`。
- 统一间距令牌建议：
  - 桌面：24
  - 平板：16
  - 手机：12

### 3.3 容器规则
- 桌面：主内容区设置 `max-width`，避免超宽屏可读性下降。
- 平板：侧栏收敛，内容以单主列为主，必要时保留辅列。
- 手机：内容区考虑底部导航与 `safe-area`，避免关键按钮被遮挡。

## 4. 全站信息架构与导航改造

### 4.1 Desktop（>=1200）
- 保留现有 AppShell 结构（侧栏 + 顶部区）。
- 一级入口维持：工作台、灵感、设置、管理（管理员可见）。
- 项目详情/写作台/管理详情为深层页，不占一级导航。

### 4.2 Tablet（834-1199）
- 侧栏改为图标栏，配合可展开抽屉显示完整标签。
- 顶部保留页面标题与关键全局操作。
- 深层页采用“主区 + 可收起次区”模式，避免强制三栏布局。

### 4.3 Mobile（<834）
- 主导航重排为：顶部栏 + 底部 Tab + 右上抽屉。
- 底部 Tab 固定四项：工作台、灵感、项目、设置。
- 管理入口置于抽屉中（管理员可见）。
- 深层路由统一提供“返回 + 页面级操作条”，减少跳转成本。

## 5. 通用组件适配规范

### 5.1 表单
- 桌面双列可保留，平板与手机转单列。
- 标签不可隐藏，错误提示紧贴字段并可视。
- 提交区在手机端固定可达，不被软键盘覆盖。

### 5.2 表格
- 桌面保留表格视图。
- 手机改为卡片明细流（每条记录可展开详情）。
- 行操作改为卡片内按钮组或底部动作面板，不依赖 hover。

### 5.3 弹窗与抽屉
- 桌面使用居中 modal。
- 手机改 bottom sheet 或全屏层。
- 确认/取消/关闭等关键动作区固定并可触达。

### 5.4 筛选与分页
- 桌面保留内联筛选。
- 手机使用筛选抽屉并回写筛选状态。
- 分页控件在手机端简化为可触达的前后翻页与当前页信息。

### 5.5 触控与状态
- 关键点击区域最小尺寸：44x44。
- 不允许关键能力只在 hover 可见。
- 状态语义不只靠颜色，补充文本或图标。

## 6. 页面级改造清单（分层渐进）

### 6.1 阶段一：全局壳层与基础设施
范围：`App.vue`、`AppShell`、`AuthLayout`、全局样式与导航容器。

目标：
- 建立三段断点基础层。
- 打通手机导航重排（底部 Tab + 抽屉）。
- 统一内容容器、滚动与安全区策略。

### 6.2 阶段二：认证页
范围：登录、注册。

目标：
- 保持桌面居中卡片体验。
- 手机端转全宽流程，保证输入、报错与提交在软键盘下可操作。

### 6.3 阶段三：作者主流程
范围：工作台、灵感、项目详情、写作台、设置。

目标：
- 桌面多栏保留；平板收敛；手机单列。
- 章节、设定、评审、模型配置等关键任务在手机端可完整执行。

### 6.4 阶段四：管理后台
范围：管理首页、管理项目详情。

目标：
- 数据主视图在手机端转卡片流。
- 行级管理操作在手机端可直接执行。
- 复杂筛选使用移动抽屉式交互。

## 7. 验收标准

### 7.1 视口覆盖
至少覆盖以下尺寸验证：
- 375x812（手机）
- 834x1112（平板）
- 1280x800（桌面）
- 1440x900（大桌面）

### 7.2 路由覆盖
以下路由不出现布局破坏与核心操作缺失：
- `/workspace`
- `/inspiration`
- `/projects/:id`
- `/projects/:id/write`
- `/settings`
- `/admin`
- `/admin/novels/:id`
- `/login`
- `/register`

### 7.3 操作覆盖
- 作者端：可登录、进入项目、执行章节相关关键操作、完成模型设置。
- 管理端：可完成常用管理操作，不出现仅桌面可执行的关键动作。

### 7.4 可访问性基线
- 键盘焦点可见。
- 表单标签、错误信息可读。
- 关键语义不只靠颜色表达。

### 7.5 工程回归基线
- 前端构建与类型检查通过。
- 关键页面不存在明显控制台报错。

## 8. 风险与规避

### 8.1 风险
- 一次性改动全站可能引入局部回归。
- 组件级适配不统一会造成视觉与交互碎片化。

### 8.2 规避
- 按阶段交付并逐阶段验收（壳层 -> 作者侧 -> 管理侧）。
- 先统一通用组件规则，再进入页面级改造。
- 每阶段结束执行固定尺寸与固定路由回归清单。

## 9. 实施顺序结论
推荐执行顺序：
1. 全局壳层与断点系统
2. 认证页
3. 作者主流程
4. 管理后台
5. 全站回归与验收

该顺序能在保证桌面稳定的前提下，逐层落地移动端完整可用能力。
